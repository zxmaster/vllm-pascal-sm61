# Bonsai-27B (Q1_0, 1-bit) в vLLM — что сделано и где предел

Дата: 18.10.2026. Задача: завести Bonsai-27B (GGML type `Q1_0`, 1-bit ternary) в
vLLM вместо llama.cpp.

## Результат коротко

- **Поддержка Q1_0 реализована** в форке `vllm-gguf-plugin`: dequant + fused GEMM
  на Triton, регистрация типа 41, наборы квант-типов для линейных слоёв и
  эмбеддингов.
- **Ядра проверены на реальных весах**: dequant — побитовое совпадение с эталоном
  (max_abs_diff = 0), GEMM — относительная ошибка 2.2e-4 (предел fp16).
- **Модель грузится в vLLM** (архитектура `Qwen3_5ForCausalLM`, 64 слоя, TQ hybrid
  корректно определил 16 full-attention слоёв), но на GTX 1050 (4 ГБ) падает
  `CUDA out of memory` на этапе размещения весов: 3.56 ГиБ allocated + 288 МиБ
  reserved, свободно 27 МиБ. Нужно ≈4.2–4.5 ГБ VRAM.
- На GPU ≥6 ГБ (например, GTX 1060 6GB) конфигурация должна запускаться без
  изменений кода.

## Где лежит код

- `vllm-gguf-plugin-q1` (separate repo) — plugin fork: `q1_0.py` for dequant and GEMM,
  `tests/test_q1_0.py`, `Dockerfile.vllm`, `scripts/patch-image-plugin.sh`.
- Image: `local/vllm-openai:sm61-v031-q1` (v031 + patched plugin).
- Profile: `.env.bonsai` + `compose.bonsai.yaml` (container `vllm-openai-bonsai`).
- Config/tokenizer: `volumes/models/Bonsai-27B-GGUF/` (generated by
  `scripts/make-bonsai-config.py` from GGUF metadata).

## Ключевые технические детали

- Формат Q1_0: 128 значений на блок, 18 байт (fp16 scale + 16 байт битов),
  значение = `bit ? +d : -d`.
- Плагин из образа v031 — НЕ upstream 0.0.5 (в нём наши runtime-патчи), поэтому
  Q1_0 накладывается на копию плагина из образа, а не на свежий клон.
- Без CUDA-ядра для Q1_0 плагин автоматически уходит на Triton GEMM (fallback),
  поэтому `.so` пересобирать не нужно.
- Тайлы для sm_61: BLOCK_M=16, BLOCK_N=64, BLOCK_K_BLOCKS=1 — 48 КБ shared memory
  (дефолтные 32/128/4 требуют 128 КБ и падают `OutOfResources`).

## Ограничение (проверено 18.10.2026, не «что-то висело»)

Перед каждым запуском GPU проверялась: `nvidia-smi` = 6 МиБ занято, единственный
процесс — сам Bonsai. Ни vLLM, ни bonsai-llm, ни vlm-server в это время GPU не держали.

Картина при OOM (воспроизводится):

```
3.59 GiB allocated by PyTorch   (веса 3.52 GiB + буферы)
0.25 GiB reserved but unallocated (фрагментация)
~0.06 GiB CUDA context
= 3.90 GiB из 3.94 GiB; свободно 29 MiB; нужен ещё блок 24 MiB
```

Перебрано без успеха: `MAX_MODEL_LEN` 2048 → 512 → 128, `MAX_NUM_BATCHED_TOKENS`
1024 → 128 → 32, `ENABLE_PREFIX_CACHING=0`, KV fp16 вместо TurboQuant,
`GPU_MEMORY_UTILIZATION` 0.97 / 0.98 / 0.99, `expandable_segments` (на Pascal
CUDA VMM не работает: «memory mapping failed»), `max_split_size_mb`,
`backend:cudaMallocAsync`, `--cpu-offload-gb` (даёт `Total CPU offloaded parameters:
0.0` — offloader вызывается до материализации GGUF-параметров), `--cpu-offload-params`,
`torch.cuda.empty_cache()` сразу после загрузки весов.

Вывод: 4 ГБ физически не хватает — с учётом фрагментации нужно ≈4.4–4.5 ГБ.
llama.cpp живёт на этой карте только за счёт mmap + частичного offload слоёв,
чего у vLLM для GGUF нет.

## Как проверить на 6+ ГБ

```bash
docker compose -f compose.bonsai.yaml up -d
# ждать ~3–5 мин (загрузка весов + Triton JIT), затем:
curl -s localhost:8000/v1/chat/completions -H 'content-type: application/json' \
  -d '{"model":"Bonsai-27B-Q1_0-GGUF","messages":[{"role":"user","content":"Привет"}]}'
```
